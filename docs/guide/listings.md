# Listing and plugin manifests

Pass the files you submit and the run lints them against the directory checklists (rules `LST-001` to `LST-028`). With a server target (`<url>` or `--stdio`) the manifests are also cross-checked against the live server, for example that the test cases' `tools_triggered` exist in `tools/list`. **Without a target** (since 0.6.0) the run is listing-only: nothing connects, rules that need a server are skipped ("no server target (listing-only run)"), and the report says listing-only, with a null score. Use it before deploy, then add the server target to cross-check. Without the options nothing changes and the LST rules are skipped ("needs --plugin-dir" / "needs --openai-manifest").

```sh
# A Claude plugin folder (the one holding .claude-plugin/plugin.json)
npx mcp-review-check https://mcp.example.com/mcp --plugin-dir ./my-plugin --target claude

# A ChatGPT plugin package: plugin.json (extensions.com.openai) or .codex-plugin/plugin.json; the package's mcp.json is read too
npx mcp-review-check --stdio "node dist/server.js" --openai-manifest ./package/plugin.json --target chatgpt

# Before deploy: the manifests only, no server
npx mcp-review-check --plugin-dir ./my-plugin --openai-manifest ./package/plugin.json
```

`--plugin-dir` checks `.claude-plugin/plugin.json` (name, description, author, version, listing URLs, icon), a README of at least 40 words, a LICENSE, `.mcp.json` (schema, `https://`/`wss://` remote URLs, exact `npx pkg@x.y.z` / `uvx pkg==x.y.z` pins, no `.mcpb`/`.dxt` bundles, no credentials in headers), no registry in `.npmrc` next to a launcher, and no system files. The files it reads, lists and skips are listed under [Which files --plugin-dir reads](#which-files---plugin-dir-reads). `--openai-manifest` checks the listing text limits, the four HTTPS listing URLs, starter prompts, brand color contrast, icons, exactly 5 positive and 3 negative review test cases, and no `clientSecret`, reviewer credentials, server headers, apps or hooks. Icons and screenshots named in the ChatGPT manifest are measured from their PNG, JPEG, WebP or SVG headers (LST-027: square icons of 48 to 4096 px, at most 5 MiB; LST-028: PNG or JPEG screenshots 706 px wide and 400 to 860 px tall). Nothing is fetched and links are not followed. The manual checklist leaves out the items these rules cover. `--verbose` prints the parsed listing on stderr with header, env and credential values removed.

Since 1.3.0 these checks follow the directory pages more closely:
- **Plugin name (LST-002):** `claude`, `anthropic` or `anthropics` as a whole word anywhere in the name (`mcp-for-claude`) is a warning, as the plugins reference gives one; at the start of the name or as the whole name it stays an error.
- **ChatGPT `mcpServers` (LST-024):** the manifest's `mcpServers` must be the string `"./.mcp.json"` (or `".mcp.json"`). An inline object, another type or another path is an error. An inline object is still read as the server map, so its URLs (LST-024) and headers (LST-023) are checked; another path is read as before.
- **SVG icons (LST-027):** an SVG logo or composer icon without a numeric `viewBox` or numeric `width` and `height` is an error ("SVG must define a numeric viewBox or numeric width and height"). When the reader cannot tell, it is a warning: the `<svg>` start tag is not closed in the first 256 KiB, or `width` and `height` use a unit such as `em` or `in` and there is no `viewBox`. A `>` inside a quoted attribute value no longer ends the tag.
- **Screenshots (LST-028):** `interface.screenshots` in a package without an MCP server (skills-only) is an error. With a server target whose `tools/list` was read, screenshots are an error when the server reports no UI output template. Without a server target that part stays on the manual checklist (MAN-024).

A path that does not exist, or is a file where a folder is wanted (or the reverse), is a usage error (exit 2) that names the flag and not the path. A file inside that cannot be read or parsed is a warning on stderr (relative path and error code only). Values that may be credentials (headers, `env`, `clientSecret`) are never quoted in a finding. In the [config file](options-and-config.md#config-file) the keys are `pluginDir` and `openaiManifest`, relative to the file; the flags win over the keys.

A plugin folder or package under review can bring its own config file. When you run the check in that folder, or with `--cwd` pointing at it, its `mcp-review-check.config.json` or `.mcp-review-check.json` is discovered and read, but it is not trusted: a discovered file sets options only. Its server (`url`, `stdio`, `args`), output paths (`output`, `jsonOutput`, `saveBaseline`), the stdio process's `cwd` and `env`, credentials (`header`, `bearer`), `active` and `activeAuth` are ignored with a warning, and stderr names the file that was applied, so `$MCP_REVIEW_CHECK_TOKEN` never goes to a server a checkout names. Its other keys (such as `ignore` or `failOn`) still change the result: to check someone else's folder on your own terms, pass `--no-config`, or your own file with `--config`. See [Config file](options-and-config.md#config-file).

## Which files --plugin-dir reads

A local run reads the folder you name, not the repository the directory clones, so it can see files the portal never gets. Since 1.1.1:

- **Read:** `.claude-plugin/plugin.json`; `.mcp.json` at the plugin root; every `.json` file that `plugin.json` names in `mcpServers` (a string or an array), when it is a `./` path inside the plugin folder; the README and LICENSE at the root; and the package-manager configuration files `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `bunfig.toml`, `uv.toml`, `pip.conf`, `pip.ini` and a `pyproject.toml` with uv settings, at any depth.
- **Listed:** every other entry (name, size, kind) for the file-count, size, binary, link, bundle and system-file checks (LST-010, LST-012, LST-013), at most 10,000 entries and 32 levels deep. Links are listed, never followed.
- **Skipped at any depth:** the VCS folders `.git`, `.hg` and `.svn` always, and the dependency and build-cache folders `node_modules`, `bower_components`, `.venv`, `venv`, `__pycache__`, `site-packages`, `.tox`, `.nox`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.turbo`, `.parcel-cache` and `.next` only when the plugin's root `.gitignore` lists them (`node_modules/`, `/venv`, `**/__pycache__/`, `a/node_modules`; read as text, git is never run, globs are not expanded). An ignored dependency's `.npmrc` is not a package source of your plugin and its files do not count toward the 512-file limit; LST-013 names the skipped folders at info. The trade-off: whatever is inside a skipped folder is not checked, so a finding there is hidden; a folder you commit (not in `.gitignore`) is walked and checked. `dist/` and `build/` are always read: a plugin often commits its built server there.
- **The `mcpServers` files** are checked by LST-006, 007, 008, 009, 011 and LST-015 like `.mcp.json`, at each rule's own severity since 1.3.0 (1.1.1 to 1.2.x reported them at info): an unpinned launcher, a credential, an `http://` URL, a package source next to a launcher only they use, and a path that is not `./`, leaves the plugin folder (`../outside.json`) or does not exist (LST-006 errors, as `claude plugin validate` and the checklist treat them). A file behind a linked folder or over the read cap is a warning: that is this tool's guard, not the directory's rule. At most 16 files are read; a bundle path (`.mcpb`, `.dxt`) stays with LST-010. A server name used in two files is checked in both.
