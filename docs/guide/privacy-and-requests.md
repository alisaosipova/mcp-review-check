# What the tool sends, privacy and redaction

## What the tool sends

By default 20 to 40 requests, about 35 to a stateful 2025-11-25 server and about 25 to a stateless 2026-07-28 one (`--verbose` lists each one), none of which change state: an unauthenticated `initialize`, `server/discover`, the SDK handshake and list calls, a GET on the endpoint (aborted after headers), an unsupported protocol version, an unknown method, a call to a tool named `mcp_review_check_nonexistent_tool`, a read of `mcp-review-check://does-not-exist`, `initialize` without an `Origin` and with three `Origin` values (on a legacy HTTP+SSE server, a GET of the event stream with each `Origin`, cut after the headers), a second `tools/list` and one fresh connection, and `GET /.well-known/openai-apps-challenge`. When the endpoint redirects to another path on the same host (`/mcp` → `/mcp/`), the protocol probes go to the redirect target, as an MCP client would. Each Streamable HTTP session the check opens, its own connections' and each one a stateful server mints for a raw `initialize` probe (the unauthenticated one and the `Origin` ones), is ended with one `DELETE`; since 1.2.0 these are sent without waiting for the answer, each within 1.5 s, so a server that holds `DELETE` open adds at most that much to the run. A run stopped by `--max-duration`, the snapshot budget or a signal ends its open sessions the same way, following a `307`/`308` redirect within the same origin (`/mcp` → `/mcp/`, at most two hops). Every connection declares the MCP Apps client capability (`extensions: {"io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}}`), so servers that register UI tools only for capable hosts show them; when a tool links a UI, one more connection without that capability lists the tools a text-only host sees (APPS-019). When the server answers 401 it also fetches the OAuth metadata documents and sends one request with an invalid bearer token; this auth probe runs at most once per run (since 1.2.0), also when a token that opened the session is later rejected on `tools/list`. Transient failures of these probes are retried (at most 3 attempts, a timeout only once); the unauthenticated `initialize` is not retried after a timeout (since 1.2.0), and when it gets no answer at all, `server/discover` and the handshake wait at most 2 s each. Once the server has stopped answering after `initialize` (`tools/list` timed out), each later request waits at most 2 s and a timed-out Origin or challenge probe is not retried (since 1.1.0), so each costs one short wait; other transient failures are still retried. With `--active` it also calls up to 50 read-only tools (at most 3 calls each) and lists the tools on up to three fresh connections whose `clientInfo.name` is `mcp-review-check`, `claude-ai` and `Anthropic` (RT-012); see [SECURITY.md](../../SECURITY.md) for `--active-auth`.

Since 0.7.0, a 2026-07-28 (modern or dual) server also gets two read-only probes, neither of which changes state: `tasks/get` with a random task id that does not exist, only when the server declares the `io.modelcontextprotocol/tasks` extension; and `subscriptions/listen` (filter `toolsListChanged`), only when it declares `listChanged` or resource subscriptions, closed as soon as the response headers arrive. Server notifications seen in responses are counted by method name only; no payloads are kept. Both probes honour `--max-duration` and the snapshot budget.

A 2026-07-28 server also gets the unsupported-version, unknown-method and missing-resource probes in their 2026-07-28 form, and two `tools/list` requests whose `Mcp-Method` header is missing or does not match the method (a server should reject both). A modern-only server (2026-07-28 without the 2025-11-25 fallback) also gets a `tools/call` for `mcp_review_check_nonexistent_tool` in the 2026-07-28 form and one `DELETE` on the endpoint without a session id, which a stateless server is expected to answer with 405 (SPEC-015). None of these change state.

## Privacy

- No telemetry. mcp-review-check talks only to the server you check and, when it answers 401, to the authorization servers its OAuth metadata names (see [What the tool sends](#what-the-tool-sends)), plus your DNS resolver.
- The report goes to stdout or to the `--output` file, and nowhere else; with `GITHUB_ACTIONS=true` also to the job log and `$GITHUB_STEP_SUMMARY`. Nothing is kept between runs.
- `--bearer` and `MCP_REVIEW_CHECK_TOKEN`, `--header` and `--env` values, URL credentials and secret-looking stdio arguments are redacted in every format (see [Redaction](#redaction) below), including when the server echoes them.
- Without `--active` no tool of yours is called. `--active` calls only tools annotated `readOnlyHint: true`; `--active-auth` creates a DCR client on your authorization server.

## Redaction

**Redaction.** One redactor covers the whole report in every format (messages, evidence, target, SARIF run properties, the markdown `rerun:` line, GitHub annotations and job summary, fatal message, stdio stderr, `--verbose` trace): `--bearer`, `--header` values, `--env` values and their parts (the password and username of a URL, the token after `Bearer`), secret query and fragment parameters (`api_key`, `token`, `#access_token`, ...), the username and password in `user:pass@` (also `https://TOKEN@host`), stdio arguments that follow a secret-looking flag (`--api-key X`, `--accessToken X`, `--token=X`, `API_KEY=X`, `"Authorization: Bearer X"`), and tokens in a known format (`sk-…`, `ghp_…`, `github_pat_…`, `glpat-…`, `xox…-`, `AKIA…`, `AIza…`, `npm_…`, `hf_…`, a JWT) as a bare stdio argument, a URL path segment or a query value under any name, including when the server echoes them on stdout, on stderr or in what it lists. Usage errors never repeat option values. Values shorter than 4 characters, `true`, `false`, `yes`, `no`, `on`, `off`, `null`, `undefined`, `none` and numbers with up to 6 digits before an optional decimal part are not treated as secrets: they would blank out unrelated report text. Nor are common settings under a plain `--env` name (`production`, `development`, `staging`, `test`, `local`, log levels such as `debug`, version numbers such as `1.2.3` or `v2.0.1-rc.1`, and since 1.2.0 the report's own words `claude`, `chatgpt`, `openai`, `anthropic`, `spec`, `all`, `stdio`, `sse`, `http`, `https`, `streamable-http`, `json`, `sarif`, `junit`, `markdown`); under a secret-looking name they are masked. A finding's catalog title and docs links and the `--target` value are never masked. Since 1.2.0 a secret is also found when it is written with escapes: each character other than a letter or digit as itself, a percent-escape with hex in either case (`%2F`, `%2f`, or `/` kept raw as Python's `quote` does), a JSON `\uXXXX` or `\/` escape, `+` for a space, or Node's `\xHH` for a control character; a secret of 8 or more characters also in any letter case. A `Cookie` header is masked pair by pair, and a session-like or token-like cookie value on its own; a `Basic` credential also by its decoded `user:pass` and password, so a server that echoes the plain password does not leak it.

**Redaction before the rules.** The rules read what the server sent with only the strong values masked: `--bearer`, `--header` values, `--env` values under a secret-looking name (`API_KEY=…`), URL credentials (a URL username only when it looks like a token) and stdio arguments after a secret-looking flag. Other `--env` values and their parts (`--env FORMAT=text`, the user and password in `--env DATABASE_URL=postgres://postgres:postgres@db/app`) are masked in the finished report and every other output only, unless a part looks like a token (a known format, or 16 or more characters with letters and digits), so a plain word there changes no finding, severity or exit code. Protocol and schema words (`object`, `string`, `title`, `type`, `properties`, `text`, `image`, `json`, `html` and the like) are never treated as secrets. Give a secret under a secret-looking name, so that it is masked before any cut (see [SECURITY.md](../../SECURITY.md)).

**Input caps.** Before the pattern rules run, metadata strings over 16 KB and UI resources over 2 MB are truncated and the report lists what was cut (JSON `limits.truncated`); names, URIs, regex patterns and other schema syntax are kept up to 1 MB, so they are compared whole. The `--active` calls' arguments, JSON-RPC and transport errors and the JSON-RPC errors observed during the run are capped at 16 KB per string too. At most 50 UI resources are read per run, and the report says when more were listed. SDK error bodies are capped at 64 KB. To bound memory on a hostile server, an HTTP response body is read up to 64 MiB (per event on an SSE stream), each listing (`tools/list` and the others) up to 64 MiB over all its pages and at most 100 pages, and a stdio message up to 64 MiB (a larger one is named as the cause of the errors that follow); of a stdio server's stdout lines that are not JSON-RPC, the first 50 are kept, with the total count.

**Server text in reports.** Text and markdown reports show control, bidi and zero-width characters from the server (ESC, CR, LF, U+202E, …) as `\u{..}`, so a server name, tool name or message cannot recolour the terminal, add a hyperlink, reorder text or start a GitHub workflow command line. Markdown reports also escape markdown syntax in server text (see [SECURITY.md](../../SECURITY.md)). JSON and SARIF keep the text as sent.
