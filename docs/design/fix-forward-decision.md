# Decision: fix-forward scope (`--write-annotations` writer vs copy-paste snippets)

Status: proposed, for the maintainer to accept or reject. Date: 2026-11-03. Version as found: `package.json` 0.7.0 on
branch `feat/user-value`; latest local tag v0.7.0 (on HEAD `888e14f`).

## Question

Should mcp-review-check gain an opt-in `--write-annotations` option that writes the missing `title` and annotation
hints into the user's server, or keep the current "FIX SNIPPETS" block that the user copies by hand?

## What exists today (read from the code)

`fixSnippets()` in `src/report/text.ts` builds one JSON fragment per tool:

- **Which tools:** a tool reported by TOOL-011 or TOOL-012 (missing annotation hints), or by TOOL-006 when the tool
  has no title at all (TOOL-006 also fires on a long or conflicting title; those tools get no snippet).
- **What it prints:** `<tool name>: {"title": ..., "annotations": {...}}`.
  - `title`: only when missing; the tool name split into words, first letter upper-case
    (`read_wiki_structure` -> `"Read wiki structure"`).
  - `annotations`: the tool's existing annotations plus each missing hint among `readOnlyHint`, `destructiveHint`,
    `openWorldHint`. The guess comes from `toolKind()` (`src/rules/util/text.ts`): a declared `readOnlyHint: true`
    counts as read and a declared `readOnlyHint: false` or `destructiveHint: true` as write; otherwise a recognized
    read verb at the start of the name (and no compound write verb) gives `readOnlyHint: true, destructiveHint: false`;
    anything else, including names with no recognized verb, gives `readOnlyHint: false, destructiveHint: true`. `openWorldHint` is always guessed `true`.
- **Where:** text format only, under the heading
  `FIX SNIPPETS (add to each tool definition; check the guessed hint values)`. `--quiet` drops the block. The
  markdown, JSON, SARIF and JUnit renderers do not include it (`grep -n fixSnippets src/report/*.ts` matches only
  `text.ts`).

The snippet is in the **wire shape** of a `tools/list` entry, not in the syntax of any SDK. The CLI only sees the
wire: it does not know which file, language or SDK call defines a tool, even with `--stdio` (it knows the command,
not the source tree).

## Measurement on the captured fixtures

Command: `npm run build && node docs/launch/evidence/snip-stats.mjs`, which loads each file in `test/fixtures/real/` the same way
`test/real-servers.test.ts` does, runs `runRules` and `fixSnippets` from `dist/`, and compares
the name heuristic with the hints the server authors declared. Aggregate only; no server is named. The fixtures are
7 public servers captured on 2026-10-22 (`test/fixtures/real/NOTICE.md`), a small sample.

| Measure | Value |
|---|---|
| Servers / tools in the fixtures | 7 / 28 |
| Tools that get a fix snippet | 16, on 3 of the 7 servers |
| Of those 16, name starts with a read verb / no recognized verb (`snippetGuessKind`, hints stripped) | 8 / 8 |
| Of those 16, title only (no hint guessed) / at least one hint guessed / `destructiveHint: true` set by default (no recognized verb) | 5 / 11 / 8 (reviewer one-off over `fixSnippets()` output, not committed) |
| Tools whose authors declared `readOnlyHint` | 20 (19 of them `true`) |
| Name heuristic agrees with the declared `readOnlyHint` | 15 of 20 |
| Disagreements: heuristic says "not read-only", author says read-only | 5 of 20 |
| Disagreements: heuristic says read-only, author says not read-only | 0 of 20 |
| Declared tools whose name has no recognized verb | 6 of 20 |

Reading: the guess errs in the conservative direction on this sample (it never claimed read-only for a tool its
author marked otherwise), but it is wrong for 1 in 4 tools that have ground truth, and half of the snippet tools get a
`destructiveHint: true` that is a default, not an inference. A value that is wrong 1 time in 4 is acceptable as a
suggestion a human reads; it is not acceptable as a value a tool writes silently.

## Options

### A. Keep copy-paste snippets (status quo)

- The user reads each value before it reaches their code; the heading already says the hints are guessed.
- No write access, no language or SDK knowledge, no new failure modes.
- Cost: manual work per tool (16 tools across 3 servers in the sample above).

### B. Opt-in `--write-annotations` writer

To be useful it must edit **source**, because the wire shape is generated by the user's code. That means:

- **Formats:** at least TypeScript SDK (`registerTool` / `tool()` calls, object literals, sometimes zod schemas built
  elsewhere), Python (FastMCP decorators, `Tool(...)` objects), plus Go, Java, C# and hand-written JSON. Each needs a
  parser or a codemod; a regex writer would corrupt code.
- **Locating the tool:** the CLI has the tool name from `tools/list` only. Names can be built at runtime, prefixed,
  generated from OpenAPI, or come from a proxy; a writer would have to search the tree and could patch the wrong
  definition.
- **Overwriting user code:** risk of clobbering formatting, comments or a deliberate omission; needs a dry run, a
  diff preview, refusal on a dirty git tree, and never touching an existing value.
- **False confidence:** a written `readOnlyHint: true` or `destructiveHint: false` is a safety claim that clients use
  to skip confirmation prompts. A wrong value written by the linter becomes the server's claim, and the next run
  reports the tool as clean (TOOL-011/012 only check that hints are present). The tool would hide its own guess.
- **Scope creep:** the project is a read-only linter ("Read-only by default" in README). A writer changes the trust
  model of a CLI that today needs no write access to anything.

### C. Machine-readable snippets (a smaller middle step)

Emit the same fragments in the JSON report (for example a `fixes` array keyed by tool name, each value marked
`guessed: true`). A user, a script or a coding agent applies them with full knowledge of the source tree. No file
writes by mcp-review-check.

## Decision

**Recommend A: keep the copy-paste snippets and do not build `--write-annotations`.** Revisit C first if users ask
for automation; B only when every condition below holds.

Rationale: the values are guesses (wrong for 5 of 20 tools with ground truth in the sample), the CLI cannot see the
source it would edit, and writing safety hints on the user's behalf turns a heuristic into an assertion that the next
run cannot catch.

## What would make B worth building

All of these, not any one:

1. Evidence of demand: repeated issues or requests from users with many tools (the sample has at most a few servers
   with many snippet tools).
2. A hint source better than the name heuristic, measured: for example agreement of at least 19 of 20 on a larger
   fixture set with declared hints, and zero "read-only" guesses for tools declared otherwise.
3. Scope limited to one SDK whose tool definitions are statically locatable (for example literal names in the
   TypeScript SDK), with an AST codemod, `--dry-run` as the default and a unified diff as output.
4. Never overwriting an existing value, refusing on a dirty working tree, and writing a marker the next run can
   report (so a guessed `readOnlyHint` stays visible as "guessed, confirm" instead of silently passing TOOL-011).

## Small follow-ups that fit option A (not applied)

- Mention in the FIX SNIPPETS heading which hints were guessed from no recognized verb (they default to destructive).
- Optionally add the fragments to markdown output for pull-request comments (option C territory; separate decision).
